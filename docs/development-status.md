项目已具备可运行的 SaaS 开发骨架和部分租户管理基础，但尚未形成 AI 助理产品闭环。当前应按既定阶段继续，不要把已有的占位页面、演示数据或最小 LangGraph 示例描述为已交付业务能力。

**截至 2026-10-22：工程底座已可用于本地开发；阶段 1（租户/组织/角色/审计）处于收尾中，阶段 2（平台模型目录、套餐权益和租户模型配置）进行中；阶段 3 的助理构建、审批、发布和真实模型运行闭环尚未开始。**因此项目仍处于产品基础建设期，PRD V1.0 的主要业务模块还没有形成可供企业实际使用的端到端能力。没有可信的完成百分比，不能把已存在的页面框架或占位页计为完成。

### 审计查询首版（PRD SET-110–113 部分）

- 新增 `0007_audit_log_query`：记录分类、结果、描述和来源 IP，并为租户时间序查询增加复合索引；历史记录无法恢复的 IP 明确返回空值。
- 提供租户隔离的审计查询 API：分类、操作人/内容搜索、结果、时间范围、分页；CSV 导出使用相同过滤条件并防护表格公式注入。
- 新增企业侧审计日志界面：筛选、分页、详情展开、来源 IP、空态/失败态和导出按钮；只具备 `audit:view` 的用户不能导出。
- 当前记录覆盖已有的租户、成员、角色、组织变更，以及登录成功/失败、退出登录和审计导出。审计事件禁止通过 SQLAlchemy ORM 更新/删除；新事件捕获请求来源 IP。
- 租户列表/导出查询仅限当前租户最近 365 天；审计完整性 API 可验证哈希链并报告旧的未链记录数。

### 审计完整性、保留与平台隔离（PRD SET-110–113 部分）

- `0008_audit_chain_and_retention` 增加平台/租户审计 scope、链序号/前序哈希/事件哈希，以及 `audit_chain_checkpoints`；新审计事件按 scope 以 SHA-256 前向哈希链存储。
- PostgreSQL 事务级 advisory lock 串行化同一 scope 的链写入；数据库触发器阻止常规 SQL 更新/删除审计记录及 checkpoint。ORM 仍保留 append-only 限制。
- 历史记录被标注为租户或平台 scope，但**不回填链哈希**；完整性接口明确返回 `unchained_legacy_events`，不能将旧历史描述为受链保护。
- `python -m beework.audit_maintenance` 可清理超过 365 天的数据并在删除链前缀前保存 checkpoint；可用 `--interval-seconds` 在进程内周期执行。Compose 增加 `audit-retention` 服务，每 24 小时运行一次；生产部署仍需将该进程纳入生产编排/调度与告警。
- 企业侧审计页显示租户哈希链校验结果；平台侧新增独立的操作审计筛选/导出/完整性校验页和 API。平台审计仅查询 `scope=platform`，不展示企业业务审计；平台创建/状态变更也会单独写入平台审计。
- 哈希链可检测数据库记录的非授权更改/删除，但不是外部 WORM：有数据库高权限的攻击者可绕过应用控制并重算链；生产环境还需外部不可变存储/密钥托管签名和访问分离。外键 `ON DELETE SET NULL` 对已引用用户/租户的修改会被 append-only 触发器拒绝，因此硬删除会失败；当前产品流程采用停用/成员关系移除，不提供租户或用户硬删除。
- 不是所有业务配置和拒绝操作都有审计事件；模型/业务 API 尚未全面落地。PostgreSQL advisory lock 的真实并发竞态尚未加入集成测试。

### 界面

- 已有企业工作区基础框架、企业侧组织/成员/角色管理界面。
- 已有独立平台控制台、平台总览、租户管理和操作审计入口；平台审计页具备筛选、导出及哈希链状态。

### 已有验证记录

本轮验证：Docker API 容器内完整 unittest 套件 21 项通过；前端 `npm --prefix frontend run build` 与 `npm --prefix frontend run lint` 通过；Python compileall、`git diff --check`、Compose 配置校验和 API readiness 通过；PostgreSQL 已应用 `0008_audit_chain_and_retention`，`alembic check` 无模型差异。`audit-retention` 容器已启动并通过首次清理（删除 0 条）。另以事务探针验证 PostgreSQL append-only trigger 会拒绝 UPDATE、保留策略事务权限允许清理，探针未留下审计记录。SQLite 单测覆盖哈希篡改检测、checkpoint 后完整性、留存清理和平台隔离/授权。浏览器人工检查确认平台管理员登录、审计导航、列表记录和完整性状态可用；未做多视口视觉回归。PostgreSQL advisory lock 的并发竞态尚未做 PostgreSQL 实测。

### 平台模型目录首版（PRD PLT-090、PLT-093 部分）

- 新增 `0009_platform_model_catalog` 与平台模型表，支持供应商、模型类型、区域、套餐开放范围/租户白名单、输入输出成本、扣点、运行限制、状态及降级模型引用。
- 平台管理员可通过平台模型目录页面创建、编辑、搜索和按状态筛选；服务端限制平台管理员访问，记录平台审计事件，禁用模型保留配置。
- API Key 使用独立 `MODEL_CREDENTIALS_SECRET` 派生 Fernet 密钥后加密入库；列表/编辑响应只返回掩码，编辑时留空保留原凭证。生产环境必须设置独立、稳定且至少 32 字符的 secret，并通过密钥管理器保存；secret 丢失/轮换前需先迁移或重新录入凭证。

## 6. 持续适用的技术与安全约束

- 继续使用模块化单体控制面；执行 Worker、知识 Worker 等按业务需要独立进程/部署，不预先拆成全套微服务。
- PostgreSQL 是业务事实源；Valkey 不保存唯一业务状态。新租户资源必须由服务端强制 tenant scope。
- 已发布执行配置使用不可变版本/快照；草稿不得改变在线执行；并发修改需要明确冲突检测。
- 所有权限在后端逐资源、逐操作检查；前端隐藏菜单仅是体验层控制。
- 模型、Embedding 和供应商请求统一通过服务端网关；禁止浏览器直接持有供应商密钥。
- 工具使用白名单、参数 Schema、最小权限、超时、幂等、网络限制和审计；不开放任意代码执行。
- 文件上传、回调/Webhook 和 URL 抓取需要在对应模块实现文件类型/大小限制、病毒扫描或安全策略、SSRF 防护和签名校验。
- 日志/追踪按策略脱敏；不默认记录完整敏感正文。平台操作与租户业务访问必须隔离并可审计。
- 每次代码修改先检查 `git status --short`；当前仓库可能含未提交改动，禁止覆盖或清理他人/前序会话的工作。
