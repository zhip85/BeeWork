# T-059 OC · 组件编排

**版本**：V0.3　**依赖**：T-054、T-041、T-043　**PRD**：3.6.8（OC-070–074）、CHN-021–023、3.7.6 末段（组件事件回传）

## 范围

1. 配置（OC-070–071）：总开关、每轮最多组件数（1–5，越界收敛）、JSON 校验失败策略（降级文本 / 重试一次 / 丢弃）、文本降级模板。
2. 注入预览（OC-072）：列出绑定本助理的渠道实例及其**已发布快照**中的组件；展开显示注入提示词全文。
3. 提示词生成（OC-073）：按模板生成中英两版，按助理默认语言选择；函数 `build_component_prompt(snapshot, oc_config, locale)` 与渠道发布弹窗（T-041 CHN-022）共用。
4. 运行时（OC-074）：只读渠道已发布快照；解析回复中的 `<标签>JSON</标签>`，按组件 schema 校验（简化 schema 与标准 JSON Schema 两种，校验器由 T-043 提供）；native / json（开放 API 响应 `widgets` 字段）/ text（降级模板）/ off；超过上限丢弃；失败按策略处理（重试仍失败降级文本）；处理结果写 trace。
5. 终端用户在组件上的操作（按钮、预约确认）以结构化事件回传，作为下一轮输入（渠道 SDK 与开放 API 增加 `event` 消息类型）。
6. 编排总览组件摘要。

## 验收标准

- [ ] 单元测试：解析多个标签、非法 JSON、schema 不符、超上限、各模式输出。
- [ ] 测试：修改组件库中组件不影响已发布渠道快照的注入内容（CHN-025）。

## 完成记录

分支 `task/T-059-oc-components`。**无迁移**。

**后端**
- 配置 `oc.components`（`runtime/oc.py`）：`enabled`（缺省开，OC-070）、`max_per_turn`（1–5，越界自动收敛）、`on_invalid`（`text` 降级为文本 / `retry` 重试一次 / `drop` 丢弃，缺省 `text`）、`text_template`（缺省 `{{title}}\n{{fields}}`）。因为开关缺省改为开，`test_assistant_oc` 里原先用“开启组件”制造 OC 差异的用例改为“关闭组件”。
- 提示词（OC-073）：`component_service.build_component_prompt(items, config, locale, channel_name)`，中英两版，渠道发布弹窗与运行时共用。运行时只在渠道快照里有可注入组件且编排开启时才往系统提示词里追加这一段（没有组件的渠道不加“请使用纯文本回复”这类噪声）。
- 运行时（OC-074，`runtime/components_stage.py`）：执行阶段之后、`pii_output` 之前的 `components` 阶段。组件来自**会话所属渠道的已发布快照**（`conversations.channel_instance_id`，渠道必须是启用或异常状态），不读组件库，所以库里再怎么改都不影响线上（CHN-025）。解析回复里已知标签的 `<标签>JSON</标签>`，用 T-043 的校验器按快照里的 schema 校验：`native` / `json` → 组件进入 `widgets`（网站挂件渲染；开放 API 在 `widgets` 字段返回）；`text` → 用文本降级模板写成文字；`off` → 不注入，模型硬要输出也丢弃；超过每轮上限的丢弃；校验失败按策略处理——`text` 把能解析出的内容降级成文字、JSON 都读不出的丢弃，`drop` 丢弃，`retry` 把问题告诉模型再答一次（用量计入），再不行就降级为文本，不会第三次。
- 因为回复里会有标签，带组件的渠道在组件阶段处理完之前不能把文字流给访客：`hold_output` 在组件生效时置位，整段回复在组件阶段之后由 `pii_output` 一次发出。**代价：这类渠道的回复不再逐字流式。**
- 追踪：组件阶段的 step 事件带 `components.blocks`（标签、模式、是否通过、问题列表、是否保留），不含用户原文与组件内容；`runs.output` 里有 `widgets` 与 `components`；`done` 事件带 `widgets`。
- 终端用户操作（范围 5）：开放 API 与挂件的聊天请求支持 `event: {tag, action, data}`（与 `message` 二选一），服务端把它转成“[用户操作] 组件 <标签> 动作：{data}”作为下一轮输入（照常经过输入侧 PII 规则）。开放 API 的聊天请求可带 `channel_id`（本租户已发布、绑定该智能体与环境的“开放 API”渠道），带了才按该渠道快照里的组件作答；响应与 SSE `done` 里有 `widgets`。
- 接口：`GET /assistants/{id}/oc/components/preview`（OC-072：绑定本智能体的渠道、各自已发布快照里的组件与模式、注入提示词全文；未发布的渠道显示不注入）；OC 总览的组件摘要（范围 6）。

**前端**：OC 的“组件编排”面板（总开关、每轮上限、失败策略、文本降级模板、各渠道注入预览可展开看全文并跳转渠道）；网站挂件 `widget.js`（版本 2）按回复里的 `widgets` 渲染四种组件（全部用 `textContent`，链接只允许 http(s)），点击按钮 / 确认预约以 `event` 发回，访客的气泡显示按钮文字。

**没做或要注意**
1. **没有用真实模型验证“模型会按提示词输出 `<标签>JSON</标签>`”**：测试里的模型是脚本化的。提示词的措辞与真实模型的遵循度需要在真实环境里试几次，必要时调整。
2. 带组件的渠道**不再流式**（见上），这是为了不把标签漏给访客；如果要保留流式，需要在流里实时识别并拦截标签，留作后续。
3. `widget.js` 没在真实浏览器里验证（只有 jsdom）；OC 面板与渠道页没有目视验收。
4. 终端用户事件只做了“转成下一轮输入”，没有校验 `tag` 是否属于该渠道的快照，也没有限制事件的频率（沿用聊天的限流）。
5. H5、微信、WhatsApp 渠道没有运行时（T-044–T-046），所以它们的 `text` / `native` 渲染还没有落地；`text` 模式的降级逻辑已在运行时通用。
6. 每轮上限的“越界自动收敛”在保存时生效；已经存下来的越界值（不会有）也会在读取时收敛。
