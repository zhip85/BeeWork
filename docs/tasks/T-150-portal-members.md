# T-150 AI 门户 · 门户成员与席位分配（租户侧）

**版本**：V0.4　**依赖**：T-149、T-142　**PRD**：演进 PRD v1.1 第 5.2、13.4、13.7、15.1–15.2、19.9；原型“AI 门户 → 门户成员”

## 数据（`models/portal_seats.py`）

- `portal_seat_rules`：租户、组织（部门，`organizations`）、是否开启；开启后该组织（含下级）全部成员获得席位。
- `portal_seat_assignments`：租户、成员（`memberships`）、状态 `assigned` / `requested`（未分配 = 没有记录或已删除）、来源 `rule` / `manual` / `auto`、`excluded`（规则部门内被单独回收，避免下次同步被重新分配）、申请原因、分配人 / 时间、审批人 / 时间、最近登录时间（门户会话建立时更新）。
- `portal_seat_policy`（每租户一行）：首次登录自动分配（布尔）、闲置回收天数（30 / 60 / 90 / 不回收）。
- 席位计算以服务端为准：**已分配数** = 开启规则组织的成员中未被排除者 + 规则外单独分配者（去重）。**可分配上限** = 硬限制时为合同席位数；宽限时为合同席位数 × 105% / 110% 向下取整；全员不限时不设上限（T-149）。

## 规则

1. 任何分配（单人、批量、通过申请、开启部门规则、首次登录自动分配）先计算分配后的已分配数，超过可分配上限则**整批拒绝、不做部分变更**（409 `portal.seats_exhausted`，提示剩余可分配数或“合同席位已用尽，请联系客户成功经理扩容”）。
2. 分配后超过合同数但未超过宽限上限时允许，响应附带“当前已超出合同 N 席位，处于宽限期”。
3. 回收规则部门内的成员 → 标记 `excluded`；关闭部门规则 → 释放该组织的规则席位，手动分配的保留。
4. 驳回申请 → 回到未分配，申请原因清空，通知申请人；通过 → 分配（受第 1 条约束），通知申请人。
5. 闲置回收：一键释放“超过回收天数未登录”的已分配席位；Worker 每日按策略自动回收（策略为“不回收”时跳过）。
6. 并发：分配在租户级串行化（`api.common.lock_tenant` 或席位计数行锁），PostgreSQL 并发测试证明不会超额。
7. 门户席位只针对员工门户；控制台成员是否占用门户席位与其他员工相同（需要用门户就要有门户席位，`unlimited` 除外）。
8. 所有分配、回收、审批、规则与策略变更写租户审计；配额用量达到 90% 时通知租户管理员（客户成功经理通知待 T-101）。
9. 注册配额用量计数器 `portal_seats`（T-149），供订阅与用量页、平台健康度读取。

## 接口与权限

- 权限沿用 `portal` 模块：`portal:view` 查看；`portal:edit` 修改规则与策略；`portal:publish` 分配 / 回收 / 审批（与上下架同级，避免构建者自行扩大使用范围）。
- `GET /portal/seats/summary`（合同授予只读、已分配 / 合同数 / 可分配上限、待审批数、闲置数、控制台席位已用 / 总数）、`GET /portal/seats/members?q=&filter=assigned|unassigned|requested|idle`（分页）、`POST /portal/seats/assign`、`/revoke`、`/approve`、`/reject`（都接受成员 ID 列表，单人即长度 1 的列表）、`GET/PUT /portal/seats/rules`、`GET/PUT /portal/seats/policy`、`POST /portal/seats/reclaim-idle`。

## 界面（AI 门户 → “门户成员”页签）

合同授予条（只读，注明由平台设定，右侧单独显示控制台席位）；统计卡（已分配 / 合同数与进度条、待审批、闲置，点击筛选）；分配规则（部门开关与人数、首次登录自动分配、闲置回收天数与“一键回收 N 个”）；成员列表（搜索、筛选、来源或申请原因、最近登录、状态，单人与批量操作，批量只作用于已勾选且当前可见的成员）。应用管理页的门户席位卡片可跳转到这里。
