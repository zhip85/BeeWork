# T-087 领域事件总线与 Webhook

**版本**：V0.3　**依赖**：T-002、T-071　**PRD**：3.10.10 Webhook（SET-091）、5.8、APR-025、SET-083、NFR-020

## 设计

- 事件总线 `beework/events.py`：`emit_event(db, tenant_id, type, payload)` 写 `domain_events`（同事务，outbox），Worker 分发给订阅者：站内通知规则（T-088）、Webhook 端点（本任务）。首批事件：`conversation.completed`（T-026）、`handoff.requested`（T-081）、`approval.updated`（T-022）、`usage.threshold`（T-011）、`assistant.published`（T-024）。已完成的任务在本任务中补上 `emit_event` 调用。
- 载荷只含 ID 与必要摘要，不含会话正文和密钥。

## 范围

1. 端点（SET-091）：地址（公网 https 校验）、订阅事件（≥ 1）、启用开关、签名密钥（只在创建时展示一次，加密存储，可轮换）。
2. 投递：POST JSON，Header 含事件名、投递 ID、时间戳、`HMAC-SHA256` 签名；经 T-071 安全出站客户端；非 2xx 或 10 秒超时为失败；按 1 / 5 / 30 分钟、之后每小时重试，最多 24 小时；连续失败 24 小时自动停用并通知租户管理员。
3. 投递记录：最近 100 次（状态码、耗时、错误、时间），“重发”与“测试”（发送测试事件并刷新最近推送）。
4. “设置 → API 与 Webhook → Webhook”页。

## 验收标准

- [ ] 测试：签名可由公开的验证示例代码复算；重试时间表（可注入时钟）；24 小时后停用；投递 ID 在重试中保持不变（接收方可去重）。
- [ ] 内网地址端点保存被拒。

## 完成记录

分支 `task/T-087-webhooks`。**迁移 `0060_webhooks`**（`domain_events`、`webhook_endpoints`、`webhook_deliveries`）。已在开发库执行；升降级与 `alembic check` 在一次性 PostgreSQL 库通过；开发栈 Worker 已重启以加载新任务。

**事件总线**（`events.py`）：`emit_event(db, tenant_id, type, payload)` 在调用方的事务里写 `domain_events`（outbox）并入队 `events.dispatch`；发出事件时先做一次廉价的“有没有人关心”检查（订阅者可带 `interested` 判断）：没人关心（这个租户没有订阅该事件的启用端点、也没有其他订阅者）就只记录事件、不排分发任务，既不给任务队列添噪声，也不改变既有流程里的任务数；有人关心才排 `events.dispatch`，Worker 把事件交给订阅者——Webhook 扇出已接上，T-088 的通知规则用 `subscribe()` 加入即可（订阅者须幂等，重试会再调一次）。事件类型固定为五种。载荷只含 ID 与必要摘要。**已补上 `emit_event` 的既有位置**：`conversation.completed`（会话结束）、`approval.updated`（提交、逐级通过、通过、驳回、撤回，APR-025）、`assistant.published`（新版本生效）、`usage.threshold`（每个阈值每月一次）；`handoff.requested` 由 T-081 在转人工产生时调用。

**Webhook**（`webhooks.py`、`api/webhooks.py`）
- 端点：地址必须是公网 https（保存时拒绝内网 / 回环 / 保留地址，400 `security.invalid_url`；每次发送时再次解析并按 T-071 的出站客户端钉住已验证的地址，不跟随重定向）；订阅事件至少 1 个且必须是已知事件；启用开关；每租户最多 20 个；签名密钥 `whsec_…` 用 Fernet 加密存储，**只在创建与轮换时返回一次**，之后只有 `whsec_••••末四位`；权限沿用“设置”（查看 / 编辑）。
- 投递：POST 紧凑 JSON（键按字母排序，所以签名与重试用同一份字节），Header 有 `X-BeeWork-Event`、`X-BeeWork-Delivery`、`X-BeeWork-Timestamp`、`X-BeeWork-Signature`（`sha256=` + HMAC-SHA256(密钥, `时间戳.原始请求体`)）；非 2xx、连接错误或 10 秒超时为失败；按 1 / 5 / 30 分钟、之后每小时重试，从事件产生起最多 24 小时，之后放弃（`dead`）；**投递 ID 在所有重试中不变**，供接收方去重；每次重试是独立的、带时刻的任务（不依赖通用任务的退避）。
- 自动停用：端点从第一次失败起连续 24 小时没有成功，就自动停用（`disabled_reason = failing`）、写审计、通知租户管理员；中间有一次成功就重新计时；手动再次启用也重新计时。
- 记录与操作：最近 100 次投递（状态、状态码、耗时、原因、次数、时间；多的自动清掉）、“测试”（发送 `webhook.test`，即使端点已停用也发，便于修好后验证）、“重发”（同一投递 ID、同一正文，给新的 24 小时窗口）、轮换密钥、删除（连同投递记录）。
- 页面：设置 → Webhook（新增页签）：添加端点、事件勾选、签名密钥只显示一次并可复制、列表（地址与密钥掩码、事件、最近推送结果、启用开关、自动停用提示）、投递记录弹窗与重发、测试、轮换、删除。
- 文档：`docs/webhooks.md` 给出事件表、请求格式、Python 与 Node.js 验签示例、应答与重试规则。

**验证**：ruff；`test_webhooks` 26 项（签名：固定公式、篡改 / 错密钥 / 改时间戳都不过，**文档里的 Python 验签示例被测试直接取出来运行**并验证重放窗口；重试时间表（可注入时钟）1 / 5 / 30 分钟再每小时，对应的独立任务与幂等键；投递 ID 与正文在重试中不变；成功结束重试并清除失败计时；24 小时后放弃；24 小时连续失败自动停用并通知 / 审计，中间成功则重新计时；停用 / 删除后取消；解析到内网地址在发送时被拒；超时是带简短原因的失败；只保留 100 条；总线：outbox 与分发任务、未知类型拒绝、只发给同租户已订阅且启用的端点且重复分发不重复发送、其他订阅者可加入；API：密钥只显示一次且加密存储、地址与事件校验、权限与跨租户 404、数量上限、再启用重新计时、测试与记录、重发同一 ID、删除清记录；真实代码路径产生的事件：智能体发布、审批各状态变化（不含标题、意见）、会话结束（不含会话与手机号文本））；全量后端（sqlite）1524 项通过、跳过 26 项；前端 tsc / lint（仍是原有 9 条警告）/ i18n / style / build；**真实 PostgreSQL 与真实 Worker**：在开发栈里 emit 一条事件，Worker 1 秒内完成分发。

**没做或要注意**
1. **没有向真实的公网 https 端点投递过**：出站客户端按设计拒绝内网地址，开发环境里没有可用的公网接收端，所以投递用模拟传输验证（含钉住地址、Host 头、签名、重试）；真实端到端需要一个公网接收端点（例如 webhook.site 或自己的服务）手工试一次。
2. `handoff.requested` 只是事件类型，等 T-081 产生转人工请求时调用 `emit_event`。
3. 通知规则（T-088）还没有订阅总线；订阅接口已留好。
4. 事件的 outbox 行（`domain_events`）目前不清理，量大后需要加保留期任务（建议跟审计 / 会话的保留策略放在一起）。
5. 页面没有目视验收。开发栈的 Worker 不会自动重载代码，合并后需要 `docker compose restart worker`。
