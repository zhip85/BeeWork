# T-165 执行层统一策略：超时、重试、熔断与审计

**版本**：V0.5（运行时架构 v2）　**依赖**：T-160、T-071、T-072、T-073、T-163　**PRD**：演进 PRD 23.2；NFR-009；`architecture-runtime-v2.md`

## 目标

图里的执行层要求每个执行器都有“鉴权 / 超时 / 重试 / 审计”。现在 T-071 只有固定的 30 秒超时，重试与限流“留给各 provider”。把策略收口到受控执行器，所有来源（MCP、API、Dify、Skill 步骤）一致。

## 范围

1. **策略解析**：对一次调用，策略 = 注册项（T-160）→ 租户默认 → 平台默认；包含 `timeout_ms`、`max_attempts`、`backoff_ms`（指数退避 + 抖动）、`retry_on`（网络错误 / 超时 / 5xx / 429）、`breaker`（失败阈值、观察窗口、半开探测间隔）。
2. **重试**：只重试**幂等**的调用——只读工具、带幂等键且来源声明支持的写操作；尊重 `Retry-After`；每次尝试都记录；总耗时受整次运行的预算约束（不会因重试拖过运行总超时）。**写操作没有幂等声明时一律不重试。**
3. **熔断**：按注册项（或来源）统计连续失败，打开后的调用立即失败（`tool.circuit_open`，附恢复时间），半开探测成功后关闭；状态存在 Valkey（无 Valkey 时进程内降级）；熔断打开时发通知给能力管理员，并在能力页显示“不稳定”（复用 T-072 的健康标记）。
4. **超时**：单次调用超时 + 运行总预算；取消运行时中断进行中的调用（能取消的来源）。
5. **审计与指标**：`tool_invocations` 扩展 `attempts`、`policy`（命中的策略来源）、`breaker_state`、各次尝试耗时；仍只存元数据，不存参数、结果、凭据。提供按能力聚合的成功率 / 平均耗时 / 熔断次数查询（供 T-168 与能力页）。
6. 各执行器接入：MCP、API、Dify（T-163）、Skill 步骤（T-164）改为从执行器取策略，删除各自的硬编码超时。

## 验收标准

- [ ] 测试：策略解析顺序；只读重试、写操作不重试、幂等写操作重试；`Retry-After`；退避不超运行预算；熔断打开 / 半开 / 关闭；取消中断；审计字段；凭据与参数不进记录。
- [ ] 回归：T-071 / T-072 / T-073 / T-075 既有用例通过。

## 不在范围

- 租户 / 平台默认策略的管理界面（先用配置文件 / 平台设置里的几个字段）。

## 完成记录（2026-11-13，Claude Sonnet 5.5）

分支 `task/T-165-execution-policy`。迁移 `0054_execution_policy`（`tool_invocations` 加 `attempts`、`policy`、`breaker_state`、`attempt_ms`；PostgreSQL 升级 → `alembic check` 无差异 → 降级 → 升级已验证）。

**后端**（`tools/policy.py` + `tools/executor.py`）
- **策略解析**：注册项自己的设置 → 平台默认（`settings.tool_timeout_ms` / `tool_max_attempts` / `tool_backoff_ms` / `tool_retry_on`，环境变量配置，默认 30 秒、不重试）。**租户级默认没有做**（没有可存放的地方，规格里“先用平台设置的几个字段”只覆盖了平台层）；解析函数留了位置。
- **超时**：每次尝试的超时 = 策略超时与整次运行剩余预算中较小者，通过上下文变量交给受控 HTTP 客户端，各来源（MCP、API、Dify）不再各自写死 30 秒。语义是 httpx 的单次读写超时（流式回答只要持续有数据就不会被它打断）。
- **重试**（审查后修订见文末）：只重试值得重试的失败——网络、超时、5xx、429（按策略的 `retry_on`），4xx（密钥错、参数错）不重试。**哪些调用可以重试**：只读的 MCP / API 工具任意瞬时失败；写操作只有来源明确声明幂等（API 工具定义里的 `idempotent`）且带执行器幂等键才重试，否则一律不重试；Dify 应用 / Skill / 子智能体这类“不知道能否重复”的调用，只在请求确定没有送达（连接失败、解析失败）时重试。等待是指数退避加抖动，上游给了 `Retry-After`（秒数形式，最多 30 秒）就按它；任何一次等待如果会超出运行预算就不再重试；等待按 0.2 秒切片检查取消。
- **熔断**：按“租户 + 工具”统计连续的瞬时失败（默认 5 次、间隔不超过 120 秒），打开后调用立即失败（`tool.circuit_open`，写明约几秒后再试），30 秒后放行一次探测，成功则关闭、失败则重新打开。状态存 Valkey，Valkey 不可用时退回进程内（并在 10 秒内不再反复尝试连接）。打开的那一刻通知租户管理员（`tool.circuit_open`），MCP 连接同时标记为连接异常（T-072 的健康标记）；注册项带 `unstable` 标志。
- **取消**：每次尝试之前、等待期间检查运行是否被取消 / 超时，抛出而不是吞掉。
- **审计与指标**：`tool_invocations` 记录尝试次数、命中的策略来源（entry / platform）、熔断状态（closed / half_open / open / opened）、每次尝试的耗时，仍然只存元数据；`GET /registry/stats?days=` 按工具给出调用数、成功率（不含被熔断拒绝的）、平均耗时、重试次数、熔断次数、被拒次数。
- ToolError / ToolHttpError 带上游的 `status` 与 `retry_after`；MCP、API、Dify 的错误都带上。

**前端**：注册中心卡片显示“不稳定”标记；注册项对话框显示近 7 天调用数、成功率、平均耗时、重试与熔断次数；重试说明更新。中英文案。

**验证**：ruff；`test_execution_policy` 16 项（策略解析顺序；超时与运行预算；只读重试与退避；按类别重试、4xx 不重试、次数上限；写操作不重试、幂等写重试、无幂等键不重试；Dify / Skill 只在未送达时重试；`Retry-After` 与上限、退避抖动范围；等待不超预算；取消中断；熔断打开 / 拒绝 / 半开探测 / 关闭、探测失败重开、4xx 不计入、间隔太久不累加、按工具独立、Valkey 故障退回进程；记录字段且凭据不入记录；统计聚合与 `unstable`）；T-071 / T-072 / T-073 / T-075 / T-163 既有用例通过；前端 tsc / lint / i18n / style；全量后端见看板。

## 代码审查与修复（2026-11-13）

审查（`/code-review high`）发现并已修复：
1. 重试等待后运行预算用完时丢失真实错误（报成 `tool.failed`、不计入熔断）：现在保留上一次的真实错误并计入熔断。
2. 子智能体内部的工具运行时没有传运行预算（`deadline`）：已传。
3. 注册项把重试条件全部取消勾选会退回平台默认的四类：现在“空”就是“什么都不重试”。
4. 半开探测遇到提供者异常或运行被取消会占着探测位 30 秒：现在归还探测位。
5. `Retry-After` 为奇怪数字字符时抛 `ValueError`：改为容错解析，只接受正的有限秒数。
6. 统计的成功率分母包含用户拒绝的写操作：分母只算 `ok` 与 `error`。
7. API 工具的 `PUT` / `DELETE` 被自动当作幂等：改为只信工具定义里明确的 `idempotent`（幂等键并不会发给上游，不能靠方法推断）。
8. 熔断在 Valkey 上每次调用多次往返、注册项列表逐条查询：`admit` 合并为一次往返，失败计数用事务，列表批量查询。
9. 平台默认策略在导入时冻结：改为每次读取设置。
