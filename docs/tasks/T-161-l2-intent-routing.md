# T-161 L2 意图判断（JEV）与路径 A / B（替代 T-058）

**版本**：V0.5（运行时架构 v2）　**依赖**：T-160、T-054、T-071　**PRD**：演进 PRD 23.1；原 PRD OC-060–064 作历史参考；`architecture-runtime-v2.md`
**取代**：T-058。分支 `task/T-058-oc-routing`（`966ca23`，未合入）作为素材；不要合入它。

## 目标

按置信度分级：明确且单一的请求走**路径 A**（直达能力，跳过 Agent），其余走**路径 B**（L3 Agent，T-162）。判断由 JEV 完成——一个专门做分类的 LLM；开发与测试阶段用普通对话模型扮演，之后专用 API 可用时用户手动切换模型。

## 设计

1. **意图分类器接口**（`IntentClassifier`）：输入 = 当前消息 + 最近上下文 + 候选能力（注册项的名称、意图描述、示例）；输出 = 候选列表（注册项 ID + 置信度 + 理由）。首个实现 `llm_json`：用租户已启用的对话模型，按 JSON 输出，解析失败 / 超时 / 出错 = 无结果。模型是配置项（`oc.intent.model_id`，空 = 智能体自己的模型），**不写死**；新增实现（专用 API）只要实现同一接口并出现在模型选择里。
2. **管线（`route` 阶段）**：① 等待中的 Dify Chatflow 会话（T-163 的会话绑定）直接回到该流程 → ② 优先规则（保留 T-058 的规则引擎：关键词 / 正则、优先级、同级按创建时间、目标须是已挂载且可用的注册项）→ ③ 从注册中心召回前 k 个候选（`registry.recall`，k 默认 8）→ ④ 分类器判断 → ⑤ 最高候选置信度 ≥ 阈值且领先第二名一个间隔（默认 0.15）→ 路径 A，否则路径 B。分类器超时 / 出错 / 无候选 = 路径 B（L3），**不报错**。
2a. **子 Agent 与知识库**也是注册项、也参与召回：命中 `direct_enabled=false` 的项（默认是子 Agent、知识库）不走路径 A，而是把它作为 L3 的“推荐能力”提示交给 L3；**FAQ 直答**（知识库项，且 FAQ 检索得分 ≥ 知识库的检索阈值并领先第二名）是路径 A 的一种：直接返回 FAQ 标准答案并带引用，不调用模型。
3. **路径 A 的执行**：
   - 参数抽取：按注册项 `input_schema` 用一次小的结构化模型调用抽取并校验（复用 `tools.schema.validate`）；缺必填、校验不过、写操作（需用户确认）→ 转路径 B，并把已抽取的部分与缺失项作为提示交给 L3。
   - 调用：经 T-071 受控执行器（权限、参数校验、凭据擦除、记录）。
   - 结果：Dify 的回答原样返回；MCP / API / Skill 的结果默认经一次不带工具的“结果整合”调用生成回复，注册项 `direct_output=true` 时原样返回。能力调用失败 → 转路径 B（带失败原因，不重复调用同一能力）。
4. **改写配合**：沿用 T-058——“仅低置信度时改写”时先用原文判断，低于改写阈值才改写后重判；没有可判断的候选时直接改写。子问题拆解的分别判断保留（每个子问题各走一遍；有直达的先答，其余交 L3 合并）。
5. **配置**（`oc.intent`，路由阶段页改名“意图路由”）：启用开关（默认关闭，理由同 T-058）、JEV 模型、置信度阈值与领先间隔、召回数 k、自定义提示词、优先规则开关与列表。**去掉**：叶子智能体目标、意图澄清、兜底（默认能力 / 固定回复 / 人工转接）——低置信度的兜底就是 L3；转人工由 L3 / T-081 处理。
6. **记录**：路由结果写入 step 事件、`done` 事件、`runs.output.route`（版本 2）：`path`（A / B）、`source`（pending / rule / classifier / none）、候选（注册 ID、名称、得分，前 k 个）、置信度、分类器耗时与失败原因、参数抽取状态、`handoff_reason`（转 B 的原因），**不含用户原文与参数值**。测试控制台显示“路由 → 路径 A · {能力名} · {耗时}”或“路由 → 路径 B（L3）”。

## 范围

1. 模型：`OCConfig.intent` 替换 `routing`（旧草稿里的 `routing` 键忽略，不迁移——T-058 未上线）；`IntentClassifier` 与 `llm_json` 实现；纯函数的决策引擎（便于单测）。
2. 运行时：`route` 阶段、路径 A 执行（抽取 → 调用 → 整合）、转路径 B 的交接（携带候选与失败原因）；执行器装配（分类器模型工厂、测试注入点）。
3. 接口与前端：意图路由面板与规则编辑（复用 T-058 的组件，目标改为注册项）、候选 / 失效检查、规则即时测试（服务端同一套匹配）、取消挂载确认（AST-065）。
4. 发布检查：规则指向失效注册项 = “高影响”（RUL-011）；阶段摘要。

## 验收标准

- [ ] 单元测试（假分类器）：规则优先；阈值与领先间隔边界；无候选 / 分类器超时 / 出错 / 输出不可用 → 路径 B；伪造的注册 ID 被忽略；挂载范围外的能力不会出现在候选里。
- [ ] 路径 A：参数抽取成功直达、缺必填转 B、校验不过转 B、写操作转 B、能力失败转 B；Dify 回答原样返回；其余结果经整合；`direct_output` 跳过整合。
- [ ] 路由记录不含用户原文与参数值；候选与得分可在运行记录里看到。
- [ ] 与改写、子问题拆解的配合测试（沿用 T-058 的用例改写）。

## 完成记录（2026-11-12，Claude Sonnet 5.5）

分支 `task/T-161-l2-intent-routing`，**无数据库迁移**（配置在 `draft_config.oc.intent`，旧的 `oc.routing` 键读取时被丢弃）。

**后端**
- `runtime/oc.py`：`IntentConfig`（开关、模型、阈值 0.7、与第二名差距 0.15、召回 K=8、FAQ 直答、自定义提示词、优先规则开关与最多 50 条规则）；`RoutingConfig` 删除。
- `runtime/intent.py`（纯函数，无数据库）：优先规则（关键词 / 正则，数字小的先、同级先创建的先；正则有 50 ms 超时）→ 注册中心召回 → 分类器（`LlmJsonClassifier`，8 秒超时，输出 JSON，失败一律返回失败而不是抛出）→ 阈值 + 差距 → 决定（`decide`）；知识库项仅在 `faq_direct` 时走路径 A；写操作、未允许直达、没有候选、分类失败 → 路径 B；参数抽取（`extract_arguments`：子智能体 / Dify 应用无需模型，其余由模型按输入 Schema 抽取，缺必填 / 校验失败 → 路径 B）。
- `runtime/route_stage.py`：`route` 阶段（替换占位）。路径 A 通过受控工具执行器调用（权限、参数校验、凭证擦除、调用记录与模型调用一致）：Dify 应用与声明了 `direct_output` 的能力，其返回即回复；其他结果交给 `execute` 阶段，**一次不带工具的模型调用**整合成回复；FAQ 直答复用检索器与 FAQ 答案（引用与命中计数不变）。路径 B：把候选、失败原因、缺失参数作为“可能相关的能力”提示给智能体。问题拆分后每个子问题各走一遍判断，能直答的先答，再由智能体合并（“子问题结果”）。改写“仅在低置信度时”由本阶段决定：先按原文判断，置信度低于改写阈值才改写再判断一次；没有意图判断时直接改写。分类器 / 抽取器任何失败都不会让运行失败。
- 执行接线：`intent_service.py`（范围 = 智能体已挂载且勾选的注册项；小范围（≤ 2K）整体交给分类器，大范围取召回 Top K；待续 Chatflow 的 `pending`）；`executor.py` 在开启时构造 `IntentRuntime`；运行的 `output.route` 与 `step` 事件携带路由记录 v2（路径、来源、目标、候选与分数、置信度、第二名、分类耗时、交接原因 / 失败代码）——**不含用户原文、参数值、分类器的自由文本理由**。
- 接口：`GET /assistants/{id}/oc/routing/targets`（范围内的能力以及能否做规则目标、原因）、`/status`（规则目标是否失效、范围内能力数）、`POST /oc/routing/rule-test`（与运行时同一匹配逻辑，不保存、不调用模型）、`GET /oc/routing/references?source_id=`（卸载前：哪些规则指向该来源）。保存校验：意图模型必须是本租户已启用的对话模型（`intent.model_unavailable`）。发布检查：`route.rule_target_invalid`（高影响，仅在意图判断与优先规则都开启时）。阶段概览一行摘要。
