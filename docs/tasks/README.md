# BeeWork 开发任务看板

> 开发负责人维护本看板。编码模型**只认领状态为「待开发」且依赖都已「已完成」的任务**，开始时把状态改为「开发中」并填写负责人，完成后改为「待验收」；只有开发负责人验收通过后才改为「已完成」。
>
> 每个任务的规格在同目录的 `T-xxx-*.md`。工程规范见 [`../architecture.md`](../architecture.md)，路线图见 [`../technical-plan.md`](../technical-plan.md)，进度记录见 [`../development-status.md`](../development-status.md)。

## 状态定义

| 状态 | 含义 |
|---|---|
| 待开发 | 规格已就绪，可以认领（依赖满足时） |
| 开发中 | 已有人认领，正在开发 |
| 待验收 | 开发者自测通过、已提交 PR/分支，等待开发负责人审查 |
| 已完成 | 开发负责人已审查代码、复跑检查并合入 main |
| 阻塞 | 缺外部条件（如供应商 Key、RAGFlow 实例），备注写明原因 |

## 闭环切片（优先线，2026-10-28 起）

目标：尽快跑通“建助理 → 对话（经 LiteLLM）→ 会话沉淀 → 记忆注入”的最小纵向闭环，再回到下方原任务图补齐其余任务。看板仍是全图，这条线只调整**先做什么**与**先做到什么程度**；切片先行的范围写在各任务规格末尾的“Txxxa”一节，其余部分仍由原任务完成。

**知识检索约定（开发负责人决定）**：本线不接真实 RAGFlow。运行时只依赖 `Retriever` 协议，临时用 `StubRetriever`，所有界面、事件、run 记录必须标明“检索：桩实现，未接真实 RAGFlow”。T-030/T-031/T-033 保持「待开发」，**桩存在期间不得把任何知识问答相关任务记为完成**；拿到 RAGFlow Key 或确定自托管方案后由 T-033 替换桩。

**切片完成的口径**：以上六项各自通过完成检查并验收后，才算“闭环（桩检索版）”完成；完成记录须写明所用模型是真实供应商还是 `mock_response`。切片只能说明架构跑通，不代表助理产品可交付（无发布/版本、无审批、无真实知识检索）。

### 推荐并行顺序

```text
第 1 批：T-001、T-003（并行）
第 2 批：T-002、T-004、T-006、T-010（并行）
第 3 批：T-005、T-011、T-020、T-022、T-023（并行）
第 4 批：T-021、T-025（并行），T-030（RAGFlow 就绪即可开始）
第 5 批：T-024、T-026、T-027、T-031、T-032
第 6 批：T-028、T-033、T-040
```

同一批内的任务尽量不改同一个文件；共享文件（`models/__init__.py`、`api/__init__.py`、`rbac.py`、`App.tsx`）只做注册一行的改动，冲突由后合入者解决。
