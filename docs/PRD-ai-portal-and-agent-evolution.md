### 1.1 文档目的

本文档固化本次迭代的产品范围、用户体验、业务规则、数据边界和验收标准，作为后续产品评审、研发补齐后端、测试回归和上线治理的统一依据。

### 1.2 状态说明

本文档中的能力按以下状态理解：

- **已实现（前端）**：已在 React/Vite 应用或独立 HTML 原型中提供界面、状态和前端交互。
- **已实现（前端模拟）**：交互可演示，数据保存在浏览器本地，但没有真实服务端、模型、认证或第三方调用。
- **产品要求**：应在生产化阶段满足，当前前端可能仅表达目标形态。
- **待接入**：尚无真实后端实现，不得将其描述为生产可用能力。

> 重要边界：当前项目主要通过 CaseData、`localStorage` 和 `sessionStorage` 保存数据。真实服务端 API、数据库、认证后端、权限后端、密钥托管、模型调用和第三方流程调用均未完整接入。

## 2. 背景与问题

平台原有信息架构中曾同时出现 Assistant/助手与 Agent/智能体概念，导致用户难以判断两者的关系，并造成创建、能力挂载、流程编排和发布入口分散。与此同时，管理员缺少统一的员工 AI 门户配置面，员工也缺少一个面向日常工作的轻量 AI 入口。

本次迭代完成以下方向的产品演进：

1. 移除旧 Assistant/助手的独立用户入口，用户可见术语统一为 Agent/智能体。
2. 将 Agent、Chatflow、Workflow 纳入统一工作台和创建体验。
3. 将能力资源、流程画布与流程连接拆分为清晰的产品边界。
4. 补齐平台、租户、智能体三级治理、记忆和运行编排表达。
5. 建立 AI 门户管理员端，使已发布资源可配置为员工应用。
6. 重构员工端 AI 门户，支持对话、项目、应用发现和个人设置。
7. 提供可脱离 React 应用独立打开的 HTML 交互原型。

## 3. 产品目标与非目标

### 3.1 产品目标

- 建立统一、可理解的智能体产品语言和信息架构。
- 支持从智能体创建、能力挂载、流程编排、治理、测试到发布的完整前端体验。
- 支持管理员将已发布的 Agent、Chatflow、Workflow 等资源受控地上架到员工门户。
- 支持员工通过统一入口发现并使用企业 AI 能力。
- 将品牌、导航、会话能力、个人设置与登录方式变成管理员可配置策略。
- 对高风险能力建立明确的状态、引用、停用、删除和审批反馈。
- 为后续接入生产数据库、权限、认证、模型与第三方服务定义产品契约。

### 3.2 非目标

本次迭代不包含以下生产能力：

- 真实大模型推理、流式回答和用量结算。
- 真实 OAuth/OIDC、SAML、LDAP、Active Directory、企业微信认证回调。
- 真实员工目录同步、组织架构同步和服务端 RBAC/ABAC。
- 真实 API Key/Secret 加密存储、轮换和审计。
- 真实 Dify、Coze、n8n、MCP、REST 或 GraphQL 服务调用。
- 真实文件上传、向量化、检索和知识库索引。
- 真实定时任务、Webhook、后台任务或跨设备同步。
- 生产级数据库、服务端审计日志、监控告警和灾备。

当前界面中的登录、回答、上传、语音、连接测试、安全扫描和部分发布行为属于前端模拟或产品表达。

## 4. 术语、导航与信息架构

### 4.1 术语统一

| 术语 | 定义 |
| --- | --- |
| 智能体（Agent） | 由指令驱动，可自主决策、选择能力并调用工具完成任务的 AI 执行单元。 |
| Chatflow | 面向多轮会话的流程编排，保留会话状态，支持追问、澄清和中断恢复。 |
| Workflow | 面向单次任务的流程编排，强调结构化输入、确定性步骤和结构化输出。 |
| 能力（Capability） | 可被智能体或应用复用的 Skill、MCP、API/连接器、Chatflow、Workflow、知识或数据源。 |
| 流程画布 | 用于设计 Chatflow/Workflow 节点及连线的编辑环境。 |
| 流程连接 | 将已发布平台画布或外部流程应用包装为可调用资源的连接配置。 |
| 门户应用 | 管理员将已发布资源配置名称、描述、分类、可见范围和模式后，呈现给员工的应用。 |
| 控制台席位 | 可登录 BeeWork 管理控制台（构建、治理、运营）的管理员/构建者账号数，原有 `seats` 字段。 |
| AI 门户席位 | 员工使用 AI 门户的授权数量，由平台按合同授予租户，再由租户管理员分配给员工。与控制台席位分别计量、分别计费。 |
| 席位权益 | 平台授予租户的门户席位上限，包括计费模式、席位数和超额策略。 |

### 4.2 导航变更

- 旧 Assistant/助手的独立导航入口不再保留。
- 用户可见的中英文文案统一使用“智能体 / Agent”，例如“创建智能体”“搜索智能体”“智能体中心”。
- 构建域的核心入口为：智能体、知识库、流程画布、能力。
- Agent、Chatflow、Workflow 共享统一工作台，但按资源类型呈现不同创建与配置项。
- AI 门户在管理端提供应用管理、门户设置、登录与身份、使用分析等配置面。
- 员工端个人中心不再占用左侧主导航，仅从左下角账号菜单进入。

### 4.3 兼容性约束

代码内部仍可能保留 `assistants`、`assistant-detail`、`agents` 等历史页面 ID、数据键或路由标识，用于兼容既有数据和跳转。这些标识不代表产品仍存在两个用户入口。后续迁移应保证：

- 不破坏历史智能体数据；
- 不因路由重命名导致深链失效；
- 不在用户可见界面重新暴露 Assistant/Agent 双概念；
- 数据迁移完成前，内部旧标识只作为实现细节。

## 5. 用户角色与权限

### 5.1 平台管理员

- 管理平台级模型、能力基线、安全规则和强制治理项。
- 配置跨租户的默认策略及平台锁定项。
- 在创建租户和合同变更时授予 AI 门户席位权益（计费模式、席位数、超额策略），并与控制台席位分开设置。
- 查看平台级运行监控、调用追踪、评测、审批和审计。
- 平台强制项不得被租户管理员或智能体创建者关闭。

### 5.2 租户管理员

- 创建、编辑、复制、测试、发布、停用智能体与流程。
- 管理租户能力目录、知识、流程连接和租户规则库。
- 将符合条件的资源添加为门户应用并配置可见范围。
- 配置门户品牌、导航、会话能力、个人设置能力和登录方式。
- 在平台授予的门户席位上限内，把席位分配给员工：部门规则、手动分配、首次登录自动分配、闲置回收和申请审批。
- 查看租户范围的运行数据、审批与审计信息。
- 不得覆盖平台锁定策略，也不得自行修改合同授予的门户席位上限。

### 5.3 租户用户 / 员工

- 仅可访问已上架且对本人可见的门户应用。
- 登录成功后还须持有门户席位才能进入门户；无席位时可提交开通申请。
- 可创建和管理自己的对话、项目、个人资料与偏好。
- 只能在管理员允许时使用文件上传、语音、个人记忆和通知等功能。
- 不得修改门户全局策略、应用上架状态、资源来源或组织可见范围。

### 5.4 权限判定原则

员工可见应用集合应满足：

`员工已持有门户席位（或租户为全员不限）` 且 `应用状态 = 已上架` 且 `员工属于应用可见范围` 且 `底层资源仍有效`。

认证（你是谁）与席位授权（你能否使用门户）是两个独立判定：认证成功不代表持有席位。

生产化后，以上条件必须由服务端判定；前端隐藏入口不能替代权限控制。

## 6. 智能体工作台

### 6.1 工作台定位

智能体工作台是 Agent、Chatflow、Workflow 的统一创建与管理界面，支持卡片/列表发现、搜索、筛选、状态识别、编辑、复制、删除、测试和发布。

### 6.2 类型差异

#### Agent

- 通过身份、角色和系统指令定义目标。
- 可基于上下文自主决策。
- 可挂载知识、Skill、MCP、API、Chatflow、Workflow 等能力。
- 可配置记忆、路由、委派和多智能体协作。

#### Chatflow

- 面向连续多轮会话。
- 支持会话级或用户级记忆范围。
- 支持开场白、历史轮数、澄清、中断和恢复。
- 适用于客服问答、政策咨询、导购和持续协作。

#### Workflow

- 面向单次、可重复的任务执行。
- 支持结构化输入字段和输出字段。
- 支持 API、定时任务和智能体工具触发。
- 适用于审批、生成、转换、同步和批处理。

### 6.3 创建流程

用户点击“新建智能体/新建流程”后，应完成：

1. 选择资源类型：Agent、Chatflow 或 Workflow。
2. 输入名称和描述。
3. 选择图标或视觉标识。
4. 对流程类资源选择来源：
   - BeeWork 原生画布；
   - 外部应用连接，如 Dify、Coze、n8n 或通用 HTTP API。
5. 外部连接需配置服务商、App ID、Endpoint、凭据引用及输入/输出映射。
6. 创建后进入编辑器，并以草稿状态保存。

必填项不完整时，创建/保存按钮应禁用并提供字段级反馈。

### 6.4 智能体编辑器

编辑器应覆盖：

- **身份与指令**：名称、描述、角色、系统指令、默认语言、回答风格。
- **模型**：主模型、备选模型、温度、最大输出等运行参数。
- **知识与能力**：挂载知识库、Skill、MCP、API、Chatflow、Workflow 和数据源。
- **记忆**：用户画像、用户记忆、会话记忆、保留期限与作用域。
- **多智能体协作**：叶子 Agent、委派描述、路由目标和协作关系。
- **流程画布**：节点、连线、条件、循环和异常分支。
- **输入输出**：字段名称、类型、必填、默认值和结构化输出。
- **触发器**：API、Schedule、Agent tool 等。
- **试运行**：输入测试、模拟输出、执行轨迹和节点状态。
- **渠道与发布**：渠道配置、版本、审批、发布和停用。

当前配置数据主要体现为 `memory`、`multiAgent`、`refs`、`collaboration`、`nodes`、`chat`、`io`、`triggers` 等字段。

### 6.5 画布节点

> **2026-11-12 作废**：自研流程画布已取消，工作流统一使用 Dify（第 23 章）。本节仅作历史记录。

画布支持以下节点类别：

- 智能体；
- 分类；
- 提取；
- Copilot；
- 人工审核；
- 连接器；
- 函数；
- 变量；
- If/Else；
- 循环；
- 注释。

节点连线必须表达执行方向；删除节点或资源后，相关连线和引用需明确标记为失效，不得静默忽略。

### 6.6 对话与运行控制

Chatflow/Agent 的会话控制应支持：

- 记忆范围；
- 历史轮数；
- checkpoint；
- interrupt；
- 最大澄清次数；
- fallback；
- 固定回复；
- 人工转接。

Workflow 的触发与输入输出应支持：

- API 触发；
- 定时任务触发；
- 作为智能体工具触发；
- 字段类型和必填校验；
- 结构化结果及失败状态。

### 6.7 多智能体协作约束

- 主智能体只能挂载叶子 Agent。
- 当前仅支持一层协作，不支持 Agent 嵌套 Agent 的多层递归协作。
- 被挂载 Agent 必须具备可用状态和清晰的委派描述。
- 失效、停用或被删除的协作引用必须在能力配置中高亮提示并要求处理。
- 发布前应阻止包含未解决失效引用的版本进入生产。

### 6.8 状态与生命周期

资源至少包含：

- 草稿；
- 已发布 / 可用；
- 已停用；
- 存在失效引用；
- 待审批或发布中（生产化目标）。

支持操作：

- 编辑；
- 复制为草稿；
- 保存草稿；
- 测试；
- 提交审批；
- 发布；
- 发布更新；
- 停用；
- 删除。

发布与停用必须提示服务影响：发布会改变后续调用版本；停用会影响智能体、流程、门户应用和 API 调用；删除可能导致引用失效。生产环境应保留版本快照、操作者、时间和变更说明。

## 7. 能力中心

### 7.1 能力范围

能力中心统一管理：

- Skill；
- MCP；
- API 插件 / 连接器；
- Chatflow；
- Workflow；
- 知识库；
- 数据源。

当前能力导航重点呈现 Skill、MCP、API 插件、Chatflow 和 Workflow；知识库有独立管理入口，但可作为智能体能力挂载。

### 7.2 通用操作

- 按类型浏览和搜索；
- 添加、上传或连接；
- 打开详情；
- 编辑配置；
- 启用、停用；
- 复制为草稿；
- 删除；
- 挂载到智能体；
- 查看可用性、来源和安全状态。

### 7.3 Skill

- 支持上传 `.zip`、`.skill` 或 `SKILL.md`。
- 可从 `SKILL.md` 读取名称和描述。
- 自定义 Skill 在启用前需经过包结构、危险脚本、密钥、权限和外部依赖检查。
- 未通过安全检查时不可标记为可用。
- 当前安全检查为前端模拟，生产环境需由隔离的服务端扫描服务完成。

### 7.4 MCP

- 支持 Streamable HTTP、SSE、stdio 等传输方式表达。
- 支持 None、Bearer token、OAuth 2.1 等认证方式表达。
- 支持测试连接并选择暴露给智能体的工具。
- 生产环境必须将 Token、OAuth 凭据和执行命令放在服务端受控存储与运行环境中。

### 7.5 API 插件 / 连接器

- 支持 REST、GraphQL。
- 支持 None、API Key、Bearer Token、OAuth 2.0 等认证配置。
- 支持 Base URL、OpenAPI Spec 或 GraphQL Schema。
- 应支持最小权限、允许域名、超时、重试、限流和敏感字段脱敏。

### 7.6 挂载与委派

能力挂载应包含：

- 能力引用；
- 最小权限；
- 允许调用的工具或操作；
- 路由目标；
- 委派描述；
- 输入输出映射；
- fallback；
- 失效状态。

停用能力后，智能体不得继续新调用；历史版本和运行记录应保留可追溯信息。

## 8. Chatflow / Workflow 流程画布与连接

### 8.1 产品边界

> **2026-11-12 更新**：“平台已发布画布”（8.2）作废，流程连接只保留 Dify 应用（8.3）；第 23 章补充了 Dify 适配器的会话绑定、流式与参数读取。

- **流程画布**负责设计和发布 Chatflow/Workflow。
- **流程连接**负责将已发布画布或外部应用包装为可复用、可调用的能力。
- 两者必须分离，避免“编辑流程”和“配置调用凭据”混在同一入口。

### 8.2 平台已发布画布

- 默认推荐选择 BeeWork 已发布画布。
- 只展示类型匹配且状态为已发布的流程。
- 无需额外外部凭据。
- 连接保存后可供智能体和门户应用调用。

### 8.3 外部应用连接

当前界面重点支持 Dify，并为 Coze、n8n、通用 HTTP API 等扩展保留产品方向。外部连接需要：

- 连接名称与描述；
- 服务商；
- Base URL / Endpoint；
- App ID；
- API 凭据引用；
- 输入字段映射；
- 输出字段映射；
- 是否流式返回。

凭据输入在界面上以密码态展示，但当前没有真实服务端 Secret 安全存储；生产化前不得将明文凭据写入前端数据、浏览器存储或构建产物。

### 8.4 异常处理

- 没有已发布匹配画布时展示明确空状态。

## 13. 租户开通与 AI 门户席位

状态：**已实现（前端模拟）**。席位权益、分配和校验均保存在浏览器本地，没有真实计费、授权或服务端校验。

### 13.1 背景与目标

原有租户只有“控制台席位”（`seats`），用来限制能登录管理控制台的管理员和构建者人数。AI 门户面向全体员工，规模和计费方式完全不同，必须单独计量。目标：

1. 平台在开通租户和合同变更时，单独授予 **AI 门户席位权益**。
2. 租户管理员在权益上限内，把席位分配到具体员工，并能看到已分配/剩余数量。
3. 员工认证成功后，还须持有席位才能使用门户；没有席位时看到明确的“暂未开通”状态，并可发起申请。

### 13.2 两类席位

| 维度 | 控制台席位 | AI 门户席位 |
| --- | --- | --- |
| 使用者 | 管理员、构建者、运营 | 全体员工 |
| 授予方 | 平台（套餐） | 平台（合同） |
| 分配方 | 平台 / 租户管理员邀请成员 | 租户管理员：规则、手动、自动、审批 |
| 数据 | 租户 `seats` | 租户 `portalMode` / `portalSeats` / `portalOverage` |
| 展示 | 租户概览、健康度、用量与账单 | 同一位置分开展示，另有租户侧“门户成员”页 |

两类席位在所有界面中必须分开显示，不得合并成一个“席位”数字。

### 13.3 席位权益（平台侧）

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| 计费模式 `portalMode` | `named` 指定用户 / `active` 按月活跃 / `unlimited` 全员不限 | 指定用户：只有分配到席位的人能用；按月活跃：按当月实际登录人数计量；全员不限：不限人数，不设席位数 |
| 门户席位数 `portalSeats` | 正整数 | 全员不限时为空；其他模式必须大于 0 |
| 超额策略 `portalOverage` | `Hard limit` 硬限制 / `Grace 5%` / `Grace 10%` | 硬限制：满额后拦截；宽限：允许超出到上限 × 105% / 110%，并提醒；全员不限时不适用 |

套餐默认值（选择套餐时自动带出，可修改）：

| 套餐 | 控制台席位 | AI 门户席位 |
| --- | --- | --- |
| 标准版 | 10 | 指定用户 · 200 · 硬限制 |
| 专业版 | 50 | 指定用户 · 1,000 · 宽限 5% |
| 企业版 | 200 | 全员不限 |

**创建租户向导**

- “套餐与期限”步骤在控制台席位下方新增“AI 门户席位”区块：计费模式（三选一卡片）、门户席位数、席位用尽时（超额策略）。
- 选择“全员不限”时隐藏席位数和超额策略，并说明不设上限。
- 校验：非全员不限且席位数 ≤ 0 时提示“门户席位数需大于 0”，不能进入下一步。
- 右侧实时摘要、确认页分别显示“控制台席位”与“AI 门户席位”，格式如“指定用户 · 1,500 · 硬限制”。
- 开通进度新增步骤“授予 AI 门户席位：指定用户 · 1,500”；成功页显示授予结果。
- 开通时为租户写入一条配额记录：名称 `AI portal seats`，上限为席位数或 `Unlimited`，告警阈值 90%，超额策略映射为硬限制/软限制。

**租户详情**

- 概览“套餐与期限”分别显示控制台席位和 AI 门户席位；健康度新增“门户席位分配”。
- “订阅与权益”页新增 AI 门户席位编辑区，可修改计费模式、席位数和超额策略；修改后显示“未保存”，与其他订阅变更一起“应用订阅变更”。
- 保存后写入平台操作记录：“合同变更 · AI 门户：指定用户 · 1,500 → 按月活跃 · 1,800”。
- 历史租户没有门户字段时，按其套餐默认值读取，不影响加载。

### 13.4 门户成员管理（租户侧）

入口：AI 门户 → “门户成员”标签页；应用管理页的门户席位卡片可直接跳转。

**页面结构**

1. **合同授予条**（只读）：“合同授予 · 指定用户 · 2,000 · 宽限 5%”，注明由平台设定、租户内不可修改、扩容需联系客户成功经理；右侧单独显示控制台席位“96 / 120”。
2. **统计卡**：
   - 已分配门户席位：已分配 / 合同数，进度条（≥ 90% 警示色，超出为超额色），下方显示剩余可分配数或“宽限期：最多 N”。
   - 待审批申请：数量，点击筛选到待审批。
   - 闲置席位：超过回收天数未登录的已分配席位，点击筛选到闲置。
3. **分配规则**：
   - 部门规则：按部门开关，开启后该部门全部成员获得席位（随企业目录同步），显示部门人数。
   - 首次登录自动分配：开启后，未持有席位的员工首次登录即自动获得席位，直到用完。
   - 闲置席位回收：30 / 60 / 90 天或不回收；“回收 N 个闲置席位”一键释放。
4. **成员列表**：
   - 搜索姓名、邮箱、部门；筛选全部 / 已分配 / 未分配 / 待审批 / 闲置。
   - 每行显示：姓名、邮箱、部门、来源（部门规则 / 手动分配 / 首次登录自动分配 / 已从规则中排除）或申请原因、最近登录、状态。
   - 单人操作：未分配 →“分配”；已分配 →“回收”；待审批 →“通过”/“驳回”。
   - 批量操作：行首勾选，或勾选“全选当前 N 人”（作用于当前筛选和搜索结果）；选中后出现“批量分配 N”（含待审批，等同批量通过）、“批量回收 N”、“清除选择”。批量操作只作用于已勾选且当前可见的成员。

**分配与容量规则**

- 已分配数 = 已开启部门规则的人数之和 − 这些部门中被排除或未持有席位的成员 + 规则外单独分配的成员。
- 可分配上限 = 硬限制时为合同席位数；宽限时为合同席位数 × 105% 或 × 110%（向下取整）。
- 任何分配（单人、批量、通过申请、开启部门规则、首次登录自动分配）都先计算分配后的已分配数，超过可分配上限则整批拒绝、不做部分变更，并提示剩余可分配数或“合同席位已用尽，请联系客户成功经理扩容”。
- 分配后超过合同数但未超过宽限上限时允许，并提示“当前已超出合同 N 席位，处于宽限期”。
- 回收属于规则部门的成员时，标记为“已从规则中排除”，避免下次目录同步被重新分配；关闭部门规则时释放该部门的规则席位，手动分配的保留。
- 驳回申请后成员回到“未分配”，申请原因清空。

**状态模型**

| 状态 `seat` | 含义 | 来源 `source` |
| --- | --- | --- |
| `Assigned` 已分配 | 可使用门户 | `rule` / `manual` / `auto` |
| `Unassigned` 未分配 | 不可使用门户 | 空，或 `excluded`（规则部门内被排除） |
| `Requested` 待审批 | 员工已申请，等待管理员处理 | 空；附 `reason` 申请原因 |

### 13.5 员工端席位校验

1. 员工通过任一已启用登录方式认证成功。
2. 检查席位：
   - 已分配 → 进入门户首页。
   - 未分配且租户开启“首次登录自动分配”，且仍有可分配席位 → 自动分配（来源 `auto`），提示“已自动为你分配门户席位”，进入首页。
   - 未分配且无法自动分配 → 显示“你暂未开通 Acme AI”：说明身份已验证但管理员尚未分配席位，提供申请原因输入框和“申请开通”按钮，以及“使用其他账号”。
   - 待审批 → 显示“申请已提交”，说明等待管理员审批，可切换账号。
3. 管理员通过后，员工再次进入即可正常使用；驳回后回到可申请状态。
4. 页面需注明：当前认证和席位校验均为前端模拟。
5. 中英文文案随门户语言切换。

### 13.6 演示数据与当前边界

- 租户侧演示租户 Acme 使用固定的模拟合同：指定用户 · 2,000 · 宽限 5%，控制台席位 96 / 120。它不在平台租户列表中，因此平台侧对其他租户的修改不会改变 Acme 的门户成员页。
- 种子数据：数字创新部 320、销售部 640、客户服务部 480 已开启部门规则；财务部、研发中心未开启；10 名代表成员，其中 Leo Li（数字创新部，员工端预览账号）默认通过规则持有席位，Ethan Xu 有一条待审批申请。
- 部门人数为演示值；成员列表只包含代表成员，不代表完整企业目录。
- “按月活跃”目前只作为权益和展示，未实现按月统计活跃人数和月初重置。
- 席位操作目前只显示操作提示，尚未写入租户侧审计日志；平台侧仅合同变更写入操作记录。

### 13.7 生产化要求

- 席位权益来自合同/计费系统，由服务端下发，租户管理员不可修改。
- 席位校验必须在服务端完成，并在每次会话建立及应用调用时生效；前端状态只用于展示。
- 分配需使用事务或乐观锁，防止并发超额。
- 部门规则对接企业目录（LDAP/AD、企业微信、SCIM），入职自动获得、离职自动释放。
- 按月活跃模式按计费周期统计去重活跃用户，并在超额时告警。
- 所有分配、回收、审批、规则和策略变更写入审计日志，并通知申请人审批结果。
- 席位用量达到告警阈值（默认 90%）时通知租户管理员和客户成功经理。

## 16. 权限、可见性与引用完整性

### 16.1 可见性

- 管理员可配置全公司、部门、组织或其他范围。
- 员工仅可见已上架且命中本人范围的应用。
- 员工不得通过修改前端存储绕过服务端权限；该要求需在后端接入后强制实现。

### 16.2 引用完整性

资源删除或停用前，应检查其是否被以下对象引用：

- 智能体；
- 多智能体协作；
- Chatflow / Workflow；
- 流程连接；
- 门户应用；
- 渠道发布配置。

若存在引用：

- 展示引用数量和对象；
- 说明影响；
- 提供前往处理入口；
- 高风险场景阻止删除；
- 允许删除时，将引用明确标记为失效。

### 16.3 最小权限

- 智能体只能获得完成任务所需的工具和操作。
- MCP/API 应支持工具级或操作级授权。
- 门户应用不能扩大底层资源权限。
- 员工身份和应用可见性应同时参与调用授权。

## 17. 错误、空状态与边界状态

### 17.1 通用要求

所有关键页面应覆盖：

- 初始空状态；
- 搜索无结果；
- 加载中；
- 保存成功；
- 字段校验失败；
- 保存失败；
- 无权限；
- 资源已停用；
- 资源已删除；
- 引用失效；
- 无认证方式；
- 网络或服务不可用。

### 17.2 典型反馈

- **无门户应用**：提示管理员尚未上架应用，员工可继续使用默认企业 AI（如已配置）。
- **无已发布流程**：提示先到流程画布发布匹配类型的流程。
- **应用已下架**：禁止新调用，说明历史会话处理方式。
- **能力已停用**：智能体配置中标记不可用并提供替换入口。
- **失效引用**：发布前集中展示并阻止发布。
- **无认证方式**：员工登录页不可伪装为可登录状态，明确联系管理员。
- **外部连接失败**：显示错误类别、测试时间和重试，不展示敏感凭据。
- **本地存储失败**：提示数据未保存，避免误报成功。

### 18.1 响应式与兼容性

- 管理端、员工端和独立原型均适配桌面、平板、移动。
- 支持现代 Chromium、Safari 和 Firefox 的当前主流版本。

- 交互控件具有可理解标签。

- 生产调用需要请求 ID、租户、用户、应用、智能体和版本上下文。

## 20. 风险与限制

| 风险 | 当前表现 | 建议 |
| --- | --- | --- |
| 前端存储不安全 | 配置和记录保存在浏览器 | 接入服务端数据库、租户隔离和权限校验 |
| 认证仅模拟 | `sessionStorage` 表示登录 | 接入标准身份协议、服务端会话和回调 |
| 凭据无真实托管 | 界面可表达密码态，但无后端 Secret 服务 | 接入加密存储、轮换、最小权限和审计 |
| 模型与外部服务未调用 | 回答、扫描、连接测试为模拟 | 建立服务端代理、超时、重试、限流和监控 |
| 删除导致引用失效 | 当前主要通过提示表达 | 建立服务端依赖图和发布阻断 |
| 历史数据结构不一致 | 旧应用可能没有 `sourceId` | 执行可回滚迁移并保留兼容读取 |
| 大型前端包 | 构建产生 chunk warning | 进行路由级拆分和模块懒加载 |
| 类型检查未清零 | 存在 TS1117、TS7053 | 定位既有错误并建立 CI 类型门禁 |
| 原型与正式端可能漂移 | 原型由 React 源码导出，但需手动重新导出 | 在构建流程中自动执行 `pnpm export:prototype` |
| 门户席位仅前端校验 | 员工可通过修改浏览器存储绕过席位检查 | 服务端在会话建立和应用调用时校验席位 |
| 席位并发超额 | 多个管理员同时分配时无锁 | 服务端事务或乐观锁，按可分配上限原子扣减 |
| 租户侧合同为固定模拟值 | Acme 门户成员页不读取平台租户记录 | 后端接入后按当前租户读取权益 |
| 席位操作缺少审计 | 分配、回收、审批仅有提示 | 写入租户审计日志并通知申请人 |

## 22. 本次迭代结论

本次迭代完成了从“助手入口分散”向“智能体统一工作台”的产品收敛，并把能力、流程、治理、管理员配置和员工使用体验串联成完整的前端产品叙事。AI 门户已具备可演示的管理员端与员工端闭环，并补齐了“平台授予门户席位 → 租户分配到员工 → 员工登录校验与申请”的席位闭环，控制台席位与门户席位分开计量，独立 HTML 原型可用于快速评审和展示。

## 23. 运行时架构 v2（2026-11-12）

本章是对第 6、7、8、9.4 章的调整，细节与代码对应见 [`architecture-runtime-v2.md`](./architecture-runtime-v2.md)，任务见 [`tasks/README.md`](./tasks/README.md)“运行时架构 v2”。

### 23.1 分级路由

- **L2 · JEV 候选意图判断**：先用优先规则；再从能力注册中心召回候选能力；再由 JEV（专门做分类的 LLM）给出候选与置信度。高置信度且单一 → **路径 A**，直接调用该能力（参数按能力的输入 Schema 抽取并校验）；低置信度、复杂或抽取不全 → **路径 B**。
- **L3 · Agent 动态规划**：ReAct 循环，读取能力注册中心，自主规划与组合调度工具；L2 的候选作为提示传入。多智能体场景下，叶子智能体是 L3 的委派工具。
- JEV 的模型是配置项：开发阶段用普通对话模型，专用 API 可用后由用户手动切换；超时或出错时走 L3。

### 23.2 统一能力注册中心

- 注册对象：Dify Workflow / Chatflow（Dify 应用）、Skill、MCP 工具、API 工具，**粒度到工具**；每项带输入 Schema、意图描述与示例、权限、超时与重试策略。
- 智能体“挂载”即授权范围：L2 直达与 L3 发现都只在已挂载的能力里进行。
- 叶子智能体不在注册中心里（它是 L3 的内部委派手段）；知识库仍是检索的数据源，不作为可直达的能力。

### 23.3 Dify 作为流程引擎

- BeeWork 不再自研 Chatflow / Workflow 画布。工作流在 Dify 里设计，以“流程连接”接入（Base URL + 应用 API Key）。
- Dify 适配器负责：会话绑定（Chatflow 多轮，后续消息回到同一个流程）、流式调用、读取应用参数以生成输入表单（门户表单模式）、错误分类与重试。

### 23.4 Skill 执行

- Skill 除了“说明型”（加载为指令，现状）外，增加“步骤型”：声明式的步骤与依赖，每步调用一个已注册能力，由 Skill 执行器调度。

### 23.5 渠道

- 新增企业微信 Copilot 与 Office 插件；WhatsApp 暂缓。

### 23.6 验收要点

- 高置信度的明确请求不经过 L3 直达能力；低置信度或参数不全进入 L3；JEV 超时进入 L3。
- 路径、候选、置信度、能力调用链在追踪与运行记录里可见，且不含用户原文。
- 注册中心之外的能力不可被直达或发现（挂载范围）。
- 自研画布的入口、接口和文案已下线。
