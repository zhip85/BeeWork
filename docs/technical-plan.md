# BeeWork 企业级 AI SaaS 技术方案与开发计划

> 版本：PRD 对齐版
> 输入依据：[BeeWork-PRD.md](./BeeWork-PRD.md)（V1.0）、[BeeWork-prototype.html](./BeeWork-prototype.html) 功能原型及“三层产品架构”示意图。
> 需求基线：原型是功能范围、页面和交互的主依据；PRD 基于原型细化字段、业务规则、权限和验收。PRD 漏写不代表原型业务功能不做；实质冲突登记后保留原型业务能力，待产品决策明确细节。仅纯演示/身份切换控件按明确约定排除。本文是开发路线图，不是生产环境部署参数或最终安全评审。

## 1. 产品目标与范围

BeeWork 面向企业，提供构建、配置、测试、发布和治理 AI 助理的统一平台，包含租户控制台和独立的 SaaS 平台运营后台。产品按三层组织：

1. **使用方（工作台）**：员工及业务人员使用企业工作台；后续可扩展 H5/小程序、企业微信、开放 API 和消息渠道。
2. **平台 TAP（造 AI、管 AI）**：管理组织和成员，构建助理、工作流、知识、技能、工具、Widget、渠道、版本、评测、运行治理与审计。
3. **引擎与基础设施（让配置跑起来）**：将平台配置编译为运行图，执行模型、检索和工具调用，并提供持久化、队列、监控与存储。

### PRD V1.0 产品范围

- **租户控制台（PRD 3.1–3.10）**：工作台；助理；Agent、Chatflow、Workflow；知识库、文档与 FAQ；Skill、MCP、API 插件；OC 六阶段请求管线；渠道实例与组件；会话、转人工、标注、评测、追踪；审批中心；组织、成员、角色、模型环境、治理、计费、开发者和审计设置。
- **平台运营后台（PRD 3.12–3.16）**：平台总览、租户与生命周期、用量账单、运维工单、套餐权益、模型目录、渠道类型、Widget 模板、行业术语、PII 规则、安全基线和平台操作审计。
- **跨域基线（PRD 第 4–7 章）**：领域数据字典、对象状态机与不可变发布快照、继承/覆盖与引用完整性、租户角色权限矩阵及 NFR。
- **范围内的案例数据功能**：PRD 3.11 案例数据工作室，以及原型中的生成示例、恢复默认、填充示例、JSON 导入/导出和重置均作为正式功能，需服务端持久化、权限隔离与审计。
- **不开发（纯演示/开发行为）**：原型中的本地配置徽标和顶栏角色切换。原型展示的正式业务页面与交互均纳入 V1.0 范围。

PRD 规定的线上请求路径是架构和验收基线：渠道认证与准入 → 输入 PII/安全规则 → 记忆 → 术语与问题改写 → 路由 → Agent/流程/知识/工具执行 → 组件编排 → 输出护栏与渠道下发 → 异步追踪、计量和 Webhook。六个 OC 配置阶段依次为 PII、记忆、术语表、问题改写、路由、组件编排；模型和工具调用统一经 AI 网关。

原型中的“仅本地模拟、不调用模型/执行节点”不是线上行为。最终验收必须以服务端持久化、租户隔离、真实状态流转和可追踪执行为准，不能以 Toast 或本地状态模拟成功。

### 交付策略

目标是交付原型所定义的完整产品功能，并由 PRD 提供规则与验收细节；不以一次性铺开所有页面为目标。先完成跨域基础，再按业务依赖做可运行闭环；每个模块都同时交付数据/API、权限、界面和测试。首个真实闭环优先采用一个租户、平台托管模型、基础助理版本与审批、知识库检索和一个渠道（开放 API 或网站），之后按路线图交付原型中的其余业务能力、渠道、平台运营与企业级集成。首期不开放任意代码执行，也不先拆分全套微服务。

## 2. 总体架构

采用图中“三层”产品结构，但首期不把每个模块都拆成独立微服务。建议以**模块化控制面 + 独立异步任务/运行 Worker + 独立基础设施**起步：部署和扩缩容边界清晰，同时降低早期分布式事务、运维和联调成本。

### 关键架构边界

- **控制面**负责组织/权限、资源配置、发布、目录、配额和审计；不在 API 请求进程里直接跑长时间流程。
- **执行面**只读取已发布的不可变版本，按版本化 DSL 编译/执行。发布新版本不改变正在运行的任务。
- **知识服务**封装 RAGFlow、解析器和向量库；平台业务代码不直接依赖 RAGFlow 的内部表结构。
- **模型网关**统一供应商协议、密钥、模型别名、超时/重试、成本统计和限流；应用只使用平台模型 ID。
- **工具执行器**对每次调用做租户归属、权限、参数 Schema、超时、幂等和审计检查。首期仅启用平台审核过的工具，不开放任意 Python/JavaScript。
- 控制面、运行 Worker、知识处理 Worker 分开伸缩；初期可共用代码仓库和基础镜像，按进程/部署单元隔离。

## 3. 技术选型建议

以下沿用架构图选型，并补齐尚未指定的应用服务和运行基础设施。

| 层次/领域 | 建议技术 | 设计要点 |
|---|---|---|
| Web 工作台 | React + TypeScript + Vite；React Flow；Formily | API 契约生成客户端类型；流程图节点只表达 DSL 配置，不在浏览器执行可信逻辑。 |
| 服务端控制面 | Python + FastAPI + Pydantic | 适配 LangGraph、RAG 和模型生态；按领域模块组织，先模块化单体，明确 API/Worker 边界。 |
| 运行时编排 | LangGraph 1.x + 自研版本化 DSL 编译器 | LangGraph 负责状态图执行；DSL 是持久化和兼容契约，禁止直接持久化任意可执行代码。 |
| 知识检索 | RAGFlow 封装服务 | 以适配器集成；支持独立索引任务、重试、删除、重建和检索评测。 |
| 文档解析 | PaddleOCR、MinerU（按文档类型路由） | 解析任务异步化；OCR/版面分析结果保留来源定位；对 PDF、表格、扫描件设置质量检测。 |
| 向量/全文检索 | Milvus 2.5+；PostgreSQL 元数据 | 用租户/知识库过滤确保隔离；数据规模或检索需求评估后再决定是否拆独立全文搜索集群。 |
| 模型网关 | LiteLLM | 仅通过服务端访问；按租户模型授权/配额；模型 ID 与供应商密钥解耦。 |
| 私有化推理 | vLLM（第二阶段） | 独立 GPU 节点和队列；将模型可用性、显存/吞吐、量化与容量成本纳入验收。 |
| 关系库 / 缓存 | PostgreSQL / Valkey | PostgreSQL 为业务事实源；Valkey 不保存唯一业务状态。 |
| 对象存储 | S3 兼容存储 | 选择云厂商对象存储或经过许可审查的自托管实现；不要默认引入 AGPL 组件。 |
| 评测/可观测性 | Langfuse、Promptfoo、Ragas | 区分生产追踪、离线回归和检索质量评测；敏感输入脱敏，设定保留期。 |
| 隐私与安全 | Presidio + 中文规则/词典 + 策略服务 | 中文 PII 检测需自建/验证规则；过滤只是补充，不替代访问控制和密钥管理。 |
| 部署 | Kubernetes + Helm | 分环境配置、滚动发布、探针、资源限额、Secret 外置；托管版可先用容器服务，不要求第一天自建集群。 |
| API/实时通信 | REST + SSE；内部任务队列 | SSE 用于流式答复/运行事件，队列处理流程运行和文档索引；跨服务事件可用事务 Outbox 保证可靠投递。 |

### 版本和开源许可门禁

在锁定依赖和向客户交付前，对**确切版本、附带组件、托管/商业功能、模型权重及模型服务条款**做法务确认。架构图中标注的许可不代表任意版本或整套部署依赖均自动符合商业分发要求。特别复核 LiteLLM 的核心与商业功能边界、MinerU 当前许可及模型权重条款、MinIO/对象存储选型；避免仅按项目名推断许可。

## 4. 核心领域模型与数据设计

所有租户业务数据携带 `tenant_id`；资源、索引、缓存键、对象存储路径和运行记录均使用一致的租户边界。建议核心实体如下：

- **身份与租户**：`tenant`、`user`、`membership`、`role`、`permission`、`api_key`、`sso_connection`。
- **助理与编排**：`assistant`、`assistant_version`、`workflow`、`workflow_version`、`dsl_schema_version`、`published_release`。
- **可复用能力**：`skill`、`tool_definition`、`connector`、`widget`、`channel_binding`、资源引用/授权表。
- **知识**：`knowledge_base`、`document`、`document_revision`、`ingestion_job`、`chunk_metadata`、`retrieval_profile`；向量内容存 Milvus，原始文件和解析产物存对象存储。
- **执行与运营**：`conversation`、`message`、`run`、`run_event`、`approval`、`feedback`、`evaluation_dataset`、`evaluation_run`、`usage_record`、`audit_event`。

设计原则：

1. 关键业务表采用 UUID 主键、创建/更新时间、状态、版本号；关键写操作记录操作者和租户。
2. PostgreSQL 对租户数据采用显式 `tenant_id` 过滤；高风险数据可增加 Row-Level Security 作纵深防御，但不能以 RLS 代替服务端授权。
3. 发布版本不可变，指向固定的 DSL、提示词、资源版本和模型配置；运行记录保存实际引用的发布版本。
4. 会话记忆按租户、助理、用户/会话范围定义 TTL、读写权限和删除机制；默认避免跨用户记忆。
5. 文件删除要有可追踪生命周期：业务元数据删除/软删、对象存储清理、向量删除、索引重建记录和失败重试。
6. 配置密钥仅存密钥管理系统或加密密文；数据库中存引用和非敏感元数据，日志绝不输出密钥/完整授权头。

## 5. DSL 与运行时设计

### DSL 生命周期

1. 前端编辑器产生受版本约束的 JSON 配置。
2. 服务端做 Schema、字段、类型、引用、权限、环路/循环上限及资源可用性校验。
3. 保存为草稿；校验通过后测试；发布时冻结配置、记录发布者和资源版本。
4. 编译器将 DSL 转为 LangGraph 节点/边和受限节点实现；Worker 只执行已发布配置。
5. 迁移 DSL 时保留旧版读取/执行能力，并提供显式迁移与回滚，而不是静默改写已发布版本。

MVP 节点类型：开始/结束、LLM、知识检索、条件分支、变量赋值、受信工具调用、人工审批、用户追问/中断。循环节点须设最大迭代次数和总时限。任意代码节点暂不开放。

### 一次运行的主要路径

1. 工作台请求运行，服务端鉴权、检查租户配额和助理发布状态。
2. 建立 `run` 与幂等键，载入发布版本；快速响应 `run_id`，通过 SSE 推送状态和 token/event。
3. Worker 执行图：按需检索、请求 LiteLLM、调用工具；每个边界做超时、重试、权限、参数校验和脱敏。
4. 可恢复节点写检查点；用户追问时将运行置为等待状态，后续消息通过原 `run_id`/conversation 恢复。
5. 结束后保存结果、用量、引用、运行轨迹及必要的审计摘要；失败明确标记并允许安全重试。

## 6. API、集成和异步任务

API 以 `/api/v1` 版本化，OpenAPI 作为前后端契约。建议的资源边界：

- `/auth`、`/tenants`、`/members`、`/roles`
- `/assistants`、`/workflows`、`/versions`、`/releases`
- `/skills`、`/tools`、`/connectors`、`/knowledge-bases`、`/documents`
- `/runs`、`/conversations`、`/approvals`、`/evaluations`
- `/usage`、`/audit-events`、`/channels`

长任务（文档索引、评测集运行、流程执行、批量重建）通过异步队列；响应返回 job/run ID，可查询状态及取消。任务消费至少一次，因此处理器须幂等。连接器和渠道使用独立适配器接口，外部回调需签名验证、防重放和限流。

## 7. 多租户安全、可靠性与运维

### 安全基线

- 登录：MVP 支持企业邮箱/密码或可信 OIDC；企业 SSO（OIDC/SAML）作为企业版/阶段二；短期访问令牌、轮换刷新令牌、MFA 能力预留。
- 授权：RBAC 起步，权限检查在服务端每个资源操作实施；区分平台管理员、租户管理员、构建者、运营者、审批者和使用者。
- 隔离：SQL 查询强制 tenant scope；对象存储、Milvus、Valkey 键和任务消息都包含租户上下文；开展跨租户越权测试。
- 提示注入：把系统指令、检索内容和工具输出视为不同信任级别；工具采用最小权限/白名单；重要写操作二次确认或审批。
- 个人信息：中文敏感信息识别、输入/输出按策略遮盖；为追踪和评测定义脱敏、采样、保留和删除规则。
- 网络/秘密：TLS、密钥托管、供应链扫描、镜像签名/来源、管理接口隔离；生产密钥不进入前端、代码、日志或评测数据。
- 审计：记录登录、配置/发布、授权变更、知识文件、工具调用和管理员操作；审计事件追加写入并限制普通管理员删除。

### 可靠性和运维

- 请求/运行均需超时、取消、限流、重试预算和幂等；避免模型/工具重试导致重复副作用。
- PostgreSQL 备份与恢复演练；向量索引可由原文档和元数据重建；对象存储版本/生命周期按合规要求配置。
- 指标：请求成功率/延迟、模型首 token/总耗时、token/费用、队列堆积、检索延迟、解析失败率、工具失败率、租户配额。
- 日志/追踪使用 `tenant_id`、`run_id`、`trace_id` 关联，但不将敏感正文作为默认日志字段。
- 目标 SLO 在试点前协商。建议首期基线：控制面 API 可用性 99.5% 月度目标；非流式管理 API P95 < 500ms（不含外部依赖）；运行响应时间按模型/检索依赖单独度量。容量和费用压测后再确定正式承诺。

## 8. 测试与质量门禁

- 单元测试：租户作用域、授权、DSL Schema/编译、配额、脱敏、幂等和状态机。
- 集成测试：PostgreSQL、Valkey、Milvus、对象存储、模型网关和知识服务适配器；外部模型调用使用可控桩/测试环境。
- 流程测试：从编辑、校验、发布到真实执行；覆盖成功、拒绝、超时、重试、人工审批、用户追问、取消、发布回滚。
- 安全测试：跨租户 IDOR、提示注入与工具权限、文件上传边界、SSRF/回调验证、密钥泄漏和审计完整性。
- RAG 评测：固定基准集衡量检索召回、答案相关性、引用正确性；不能只以“回答看起来合理”作为验收。
- 前端测试：核心表单校验、流程图保存/恢复、权限状态、加载/失败/空状态及关键路径 E2E。
- 发布门禁：格式/lint、类型检查、单测、集成测试、依赖/镜像扫描、迁移检查；灰度发布并监控错误率。

## 9. PRD V1.0 优先级与开发路线图

按架构依赖和可验收业务闭环排序，不按原型页面数量平均分配。优先级定义：**P0** 为所有业务域的阻塞底座；**P1** 为首个真实业务闭环的必需功能；**P2** 为 V1.0 核心能力扩展；**P3** 为商业运营、企业集成和规模化交付。阶段按顺序推进；阶段内仅在接口和数据契约稳定后并行。

### 当前实现基线（已检查仓库）

| PRD / 架构范围 | 当前状态 | 结论 |

### 阶段 7 / P2：运营、审批中心、评测与可观测

**PRD：** 3.8–3.9、3.10.9–3.10.12、4.10–4.12、NFR-010–012/020。

**任务：**

3. 完整审批中心、通知、Webhook/outbox、超时提醒和失败重试；按权限脱敏日志与会话内容。
4. 建立租户/助理/模型维度用量、预算告警、速率限制和健康指标。

**验收：** 运营数据来源于真实执行事件；评测可复跑并绑定助理/知识/模型版本；Webhook 重试幂等；会话导出受授权和审批约束；追踪保留期遵守套餐和合规策略。

## 10. PRD 待确认项与实施默认值

以下事项来自 PRD 8.3、原型/PRD 差异或生产落地所需决策。不会阻断无关模块；涉及模块开始实现前，必须确认或记录采用的可逆默认值，不能把临时口径描述成已确认产品决定。功能范围以原型为准；差异项只决定实现细节，不默认删除原型能力。

|---|---|---|

| 两级审批权益 | PRD 建议仅企业版允许两级；须与套餐权益和租户审批策略一致 | 阶段 3 审批引擎 |

## 11. 模块逐个完成的执行约定

当前逐模块进度、最近验证、未完成项及交接模板统一记录在[开发进度与交接记录](./development-status.md)；本文件继续作为架构和阶段路线图。

1. 一个模块开始前先列出对应 PRD 编号、依赖、数据对象/状态机、权限、API、页面及可测验收条件；未决问题只冻结受影响部分。
2. 按「领域模型与迁移 → 服务/API 和授权 → 前端真实数据与状态 → 自动化测试 → 文档与验收」完成同一垂直切片，不先做全站静态页面。
3. 所有新业务资源默认带 `tenant_id`、审计字段、软删除与 `row_version`；创建和读取均由服务端校验租户、对象范围、状态和套餐权益。
4. 异步任务必须幂等、可重试、能显示进度和失败原因；线上执行引用不可变版本/快照；草稿不得意外覆盖生产状态。
5. 保留现有深绿、暖金、浅色工作区视觉体系；交互、文案和状态按 PRD，响应式/键盘焦点/ARIA 不因视觉复用而省略。
6. 一模块通过质量门禁后再进入下一模块；不跳过前置阶段，也不把 mock、演示数据或前端本地状态记为完成。

**当前进度：** 阶段 1（租户/组织/角色/审计）收尾中，阶段 2（模型与商业配置）进行中；阶段 3 的助理构建、审批、版本和真实运行尚未开始。详见[开发进度与交接记录](./development-status.md)及本章 PRD/原型功能交付清单。执行顺序为：先补阶段 1 授权/审计并发验证等收尾项，同时完成阶段 2 租户环境模型配置、套餐权益和配额；供应商与区域决策完成后再接真实网关；随后进入阶段 3 的助理端到端闭环。阶段 4–9 的知识、编排、渠道、运营、平台完整功能和生产交付均属于待开发范围，不因当前存在原型页面或侧栏入口而视为完成。
